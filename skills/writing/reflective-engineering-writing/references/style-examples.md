# 风格校准样例

以下为 Grilling 中用于校准的合成片段，不是作者已发表的文章，也不是实际实验结果。作者选择 B 为主、C 为辅。样例用于学习叙事节奏和语气，不代表作者确认了其中每个技术观点。

## B：个人思考型（主要参考）

### 当写代码变得越来越容易

如果实现一个想法只需要原来十分之一的时间，我们应该做什么？

最直接的答案是做更多的事情。但我对这个答案有所保留。

软件开发中有相当一部分复杂度，恰恰来自那些原本不需要实现的功能。当实现成本下降，我们也更容易制造不必要的复杂度。

从这个角度看，AI Coding 对工程师提出了一个新的要求：除了知道怎么做，还需要更清楚地知道什么值得做，什么不应该做。

我对这种变化持乐观态度。工程师可以把更多精力放在理解问题和创造价值上，而不必将大量时间消耗在重复性的实现工作中。

## C：同行交流型（辅助参考）

### 有了 AI，我们应该写更多代码吗？

一个有意思的现象是，AI 让我们写代码的速度越来越快，但判断一段代码是否有必要存在，并没有因此变得更容易。

假设一个原本需要两天开发的功能，现在两个小时就能完成。我们可能会因此更愿意接受一些过去会拒绝的需求。

但功能上线之后，维护成本并不会因为代码是 AI 写的而消失。

所以，在讨论 AI Coding 带来的效率提升时，我更关心节省下来的时间被用在了哪里。是实现更多功能，还是更深入地理解用户需求、改善系统设计、验证已有的想法？

这两种选择可能会带来截然不同的长期结果。

## 反例：形式完整但内容空泛

在当今快速发展的技术生态中，开源项目的商业化既是机遇，也是挑战。如何在保持开源精神的同时实现可持续发展，成为每一位开源维护者必须面对的重要课题。

商业化不仅仅是盈利，更是价值创造与生态建设的有机结合。

问题：没有具体问题、信息增量或可检验的判断。可直接从“既然软件可以免费使用，用户为什么还愿意付费？”切入，再讨论实际用户需求和收费设计的关系。

## 校准方法

优先学习 B 的个人思考、问题引入和自然节奏，借鉴 C 的具体假设和同行交流感。在架构分析和教程中提高技术精确性。不要每篇都以反问开头、使用第一人称或以乐观结论收尾。真正的作者声音来自内容和判断，而非句式复刻。
